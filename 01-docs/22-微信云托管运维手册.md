## 1. 架构部署总览

```
用户 ──> 微信小程序 / H5
           │
           ▼
    微信云托管 API 网关（公网）
           │  内网互通（同一 VPC）
           ▼
  ┌─────────────── 11 个服务 ───────────────┐
  │ auth(3001) user(3002) asset(3003)      │
  │ benchmark(3004) template(3005)         │
  │ billing(3006) workbench(3007)          │
  │ notification(3008) order(3009)         │
  │ media-worker(3010) admin(3011)         │
  │ admin-web（静态托管，内网访问）         │
  └──────┬───────────────┬─────────────────┘
         │               │
  云托管 Postgres  云托管 Redis
         │
  上海 VPC 内网 ──> Temporal Server（CVM 独立部署，7233 gRPC）
  云托管 COS/OSS（种子龙头凭证经 STS）
```

### 关键约束（必须遵守）

1. **服务间通信走内网域名**，禁止 localhost fallback（代码已 fail-closed 硬校验）
2. **不需要 Nginx / docker-compose.prod.yml** — 云托管自带 API 网关，管理容器编排
3. **Dockerfile 无 HEALTHCHECK** — 由云托管探针接管（观测 `/livez` `/readyz`）
4. **Temporal 走 VPC 内网 IP 连 7233**，不暴露公网；`TEMPORAL_MOCK_MODE` 生产必须 `false`

## 3. 环境变量配置

- **生产配置入口**：微信云托管控制台（服务 → 环境变量），**禁止写入镜像或仓库**
- **敏感变量清单**：

| 变量                                                                      | 说明                              | 生产要求                            |
| ------------------------------------------------------------------------- | --------------------------------- | ----------------------------------- |

## 4. 启动顺序与依赖

```
1. Postgres / Redis（云托管托管实例，先行就绪）
2. Temporal Server（CVM 内网，namespace 预注册 `reelclone-default`）
3. 无依赖服务：auth / user / asset / admin（可并行）
4. 领域服务：benchmark / template / billing / workbench / notification / order
   （依赖 3 完成后启动，内部有重试即可，无严格串行）
5. media-worker（依赖 Temporal + OSS + FFmpeg）
6. admin-web 静态托管（依赖 admin-service）
```

> 各服务启动时 `getOrThrow()` 校验关键环境变量，缺配置即 fail-fast，便于发现配置遗漏。
> 全链路就绪验证：`GET /readyz` 返回 `{"db":"up","redis":"up"}`。

## 6. 可观测性

### 6.1 端点

| 端点           | 用途                  | 说明                                       |
| -------------- | --------------------- | ------------------------------------------ |
| `GET /livez`   | 存活探针（liveness）  | 进程存活即返回 200                         |
| `GET /readyz`  | 就绪探针（readiness） | 校验 DB / Redis 连通，任何依赖异常返回 503 |
| `GET /metrics` | Prometheus 指标       | HTTP 请求量/耗时、Outbox 指标              |
| `GET /health`  | media-worker 专用     | 返回 worker 运行状态 + taskQueue           |

### 6.2 云托管告警建议指标

- `/readyz` 503（服务不可就绪）→ P1 告警
- HTTP 5xx 比例 > 1%（10 分钟窗口）→ P1
- P95 请求耗时 > 2s → P2
- Temporal Workflow 持续失败计数 → P1
- Outbox 堆积（挂起消息数持续增长）→ P2

### 6.3 链路追踪（T-5 已完成）

- **已接入 W3C Trace Context**：全服务响应头携带 `traceparent`（`00-<traceId>-<spanId>-<flags>`），同链路跨微服务传播
- **日志关联**：Pino 日志自动注入 `traceId/spanId` 字段，`x-trace-id` 保持向下兼容
- **排查用法**：前端/客户端请求响应头取 `x-trace-id` → 云托管日志平台按 `traceId` 过滤，即可串起整条调用链
- **后续演进**：接入 OTel Collector / Jaeger 时，`traceparent` 已天然兼容（标准格式），无需改造业务代码

### 6.4 已知缺口（后续补）

- 进程级指标（内存/CPU）默认不开放，由云托管面板承载
- admin-service 操作审计日志待补

## 7. 发布流程（CI → 云托管）

```
1. 代码 push master → GitHub Actions CI（13 jobs：lint/typecheck/test/build/镜像/E2E）
2. CI 通过后构建镜像并 push 到云托管镜像仓库（11 个服务 Dockerfile 已标准化）
3. 云托管控制台下发新版本：
   - 灰度发布（先 media-worker / template，再核心领域服务）
   - 每服务重启间隔建议 ≥30s，避免雪崩
4. 就绪验证：
   - 云托管探针自动调用 /readyz
   - 手动抽查 /metrics 返回 HTTP 指标
   - E2E smoke：登录 → 可用余额 → 提交生成任务 → 收到通知
5. 回滚：云托管控制台选择上一版本重新下发（无代码回滚，仅镜像版本回退）
```

### 更新镜像约束

- 多阶段构建 + alpine + `npm prune --production --legacy-peer-deps`（体积已优化，见 04-开发运维计划.md）
- `.dockerignore` 已排除 test/coverage/.git/01-docs

## 8. 常见问题排查 SOP

| 症状           | 可能原因                                 | 排查路径                                                                           |
| -------------- | ---------------------------------------- | ---------------------------------------------------------------------------------- |
| 服务启动失败   | 环境变量缺失                             | 看启动日志 `Missing ... environment variable`（getOrThrow 提示变量名）→ 控制台补全 |
| `/readyz` 503  | DB/Redis 不通                            | 检查云托管托管实例状态；确认相同 VPC 与网络配置                                    |

| Mock 被拒绝    | production 下 Mock=true                  | 已 fail-closed 抛错——正确配置真实凭证                                              |
| 权限 403       | OpenFGA 未同步                           | 检查 FGA store 写入 + 用户关系绑定                                                 |
| WebSocket 断连 | notification-service 不稳                | 客户端指数退避重连（已内置）                                                       |

## 9. 危机处理

- **P0 事故**：立即回滚镜像版本 → 止血 → 事后按质量节拍 Bug 反思 5 步（根因 → 逃逸 → 系统漏洞 → 回归测试 → 预防）
- **密钥泄露**：立即轮换 JWT_SECRET / WECHAT_PAY_PRIVATE_KEY / 云托管密钥 → 改密踢下线机制自动使旧 token 失效 → 复查 git 历史是否有明文字段
- **支付重复入账**：以订单事务 + 幂等表为准，禁止在回调外手工改账；使用 billing 幂等接口重放

## 11. 密钥管理（JWT 轮换 / 云托管密钥版本）

> 适用：JWT_SECRET、WECHAT_PAY_PRIVATE_KEY、FORMANCE_LEDGER_SECRET、AES 主密钥等**敏感变量**的变更与版本管理。
> 原则：**密钥变更必须走「新版本 + 新环境变量 → 发布新版本」链路**，禁止直接修改运行中实例的环境变量（不可审计、不可回滚）。

### 11.1 JWT 签名密钥轮换流程

**背景机制**（代码事实，勿凭印象操作）：

- 全部服务共用 `JWT_SECRET`（HS256 签名），生产环境 `resolveJwtSecret()` 强制长度 ≥ 32 字符，不足即拒绝启动。
- 签发/校验侧：auth-service 用同一密钥签发 access（默认 1h）与 refresh（默认 7d）；各服务 `ServiceJwtModule` 用同一密钥校验。
- 会话级踢下线（改密/封禁）走 Redis `user:password-changed:{userId}`，只使对应用户的旧 token 失效，**不影响其他用户**。
- **轮换 JWT_SECRET 会使全体已签发 token 验签失败**（含 refresh token），效果等于全量强制下线、全部用户需重新登录。这是预期行为，需在维护窗口内执行。

**计划内轮换步骤**：

1. **窗口选择**：低峰时段（建议凌晨 02:00-05:00），提前 1 周公告维护；云托管控台打开对应服务维护公告/降级提示。
2. **生成新密钥**（≥32 字符，建议 64）：

   ```
   openssl rand -base64 48   # Linux/macOS
   ```

   PowerShell：`[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(48))`

3. **更新配置**：云托管控制台 → 各服务 → 新建版本 → 环境变量中替换 `JWT_SECRET`（**所有服务同步替换**，auth/user/asset/benchmark/template/billing/workbench/notification/order/admin/media-worker；漏改任一服务会导致该服务鉴权不一致）。
4. **发布**：新版本先灰度（单实例）→ 观察 auth 401 率与 `GET /readyz` → 全量发布。**分批部署期间新旧版本并存**，会出现跨服务 401/验签失败，属预期，尽量缩短切换窗口。
5. **验证**：
   - 老 access token 请求任一受保护接口 → 401（验签失败），符合预期。
   - 新登录用户完整走通：login → access → 业务接口 → refresh。
   - 监控面板：auth 401 率回落、登录成功率恢复正常。
6. **回滚预案**：若异常扩散，云托管回滚到含旧 `JWT_SECRET` 的上一个版本，立即恢复旧密钥（旧 token 重新有效）。
7. **变更登记**：在 `01-docs/21-安全审计报告.md` 记录轮换时间、原因、操作人、验证结果。

**泄露应急**（见 §9 危机处理）：

- 立即执行上述 2-4 步（可跳过公告，直接全量轮换）+ 复查 git 历史/日志是否有明文字段 + 检查云托管密钥被谁查看过。

**轮换周期建议**：至少每 12 个月一次；发生泄露、疑似泄露、员工离职持有访问权限、或供应商通报时立即轮换。

### 11.2 云托管密钥版本管理规范

腾讯云微信云托管（基于 CloudBase Run）：**每个发布版本快照一组环境变量**，版本即密钥版本的载体。

| 实践     | 要求                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------- |
| 变更方式 | 仅通过「新建版本 → 修改环境变量 → 发布」；禁止编辑运行中版本的环境变量                             |
| 版本保留 | 保留最近 ≥ 5 个版本（携带密钥快照，作为回滚凭据）；版本精简前确认最近的密钥基线                    |
| 泄露追踪 | 云托管控制台访问审计（谁在什么时间查看了环境变量）定期复核；密钥变更操作人需留痕                   |
| 存储边界 | 密钥只存在于云托管控制台/密钥管理；禁止写入镜像、仓库、日志、配置仓库（`.env` 不提交）             |
| 大块值   | `WECHAT_PAY_PRIVATE_KEY` 等 PEM 大块值用 base64/JSON 字符串放入环境变量，换行以 `\n` 转义          |
| 周期巡检 | 每季度核对一次：密钥强度、轮换到期提醒、访问审计、遗留明文扫描（`node scripts/_scan-env.js` 辅助） |

**关联会话控制**：改密 / 封禁自动置 `user:password-changed:{userId}` Redis key，对应用户的旧 access/refresh token 立即失效，无需等 JWT 过期；该 key 由 JwtStrategy 在每次鉴权时检查。

### 11.3 微信支付回调（Webhook）签名密钥轮换提醒（T-6 已完成）

**适用对象与密钥角色**（代码事实，勿凭印象操作）：

| 密钥                       | 环境变量                                                | 用途                                                                              | 轮换方式                                                         |
| -------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 商户 APIv3 密钥（32 字符） | `WECHAT_PAY_API_V3_KEY`                                 | AES-256-GCM 解密回调 `resource` 密文；生成回调应答/查询请求签名                   | **人工轮换**（商户平台操作）                                     |
| 商户证书私钥 + 序列号      | `WECHAT_PAY_PRIVATE_KEY` / `WECHAT_PAY_SERIAL_NO`       | 下单/查单等出站请求的 RSA-SHA256 请求签名                                         | **人工轮换**（商户平台申请新证书）                               |
| 微信平台证书               | 自动拉取（WechatPayAdapter 定时刷新，当前 12 小时间隔） | 验签回调 `Wechatpay-Signature`（SHA256-with-RSA，按 `Wechatpay-Serial` 匹配公钥） | **自动轮换**（微信侧签发，适配器自动缓存多张证书），无需人工操作 |

**回调入口**：`POST /api/v1/webhooks/wechat-pay`（支付）与 `POST /api/v1/webhooks/wechat-pay-profit-sharing`（分账），验签必须使用 `req.rawBody`（已由 `rawBody: true` 启用）。

**轮换周期提醒**：

- `WECHAT_PAY_API_V3_KEY`：至少每 **12 个月**轮换一次；泄露/疑似泄露/供应商通报时立即轮换。
- 商户证书（`WECHAT_PAY_PRIVATE_KEY` + `WECHAT_PAY_SERIAL_NO`）：随商户平台证书有效期到期前 **1 个月**申请续期；平台到期自动停单，勿拖到最后。
- **季度巡检**（与 §11.2 密钥巡检同频）：核对 APIv3 密钥轮换到期时间、平台证书自动拉取日志无持续报错、`Wechatpay-Serial` 验签失败率接近 0。

**计划内轮换步骤**（APIv3 密钥或商户证书，影响 Inbound 回调验签 + 出站请求签名）：

1. **窗口选择**：低峰时段，通知涉及订单/分账对账的操作同学（轮换期间回调验签失败会返回 FAIL，微信会在数小时内重试）。
2. **商户平台操作**：在微信支付商户平台完成 APIv3 密钥重新设置（或申请新商户证书），记录新 KEY / 新私钥 + 新序列号。
3. **更新配置**：云托管控制台 → order-service → 新建版本 → 替换 `WECHAT_PAY_API_V3_KEY`（和 / 或）`WECHAT_PAY_PRIVATE_KEY` + `WECHAT_PAY_SERIAL_NO`（PEM 大块值 base64/JSON 存放，换行 `\n` 转义）→ 灰度发布。
4. **验证**：
   - 回调线上自测：真实小额支付触发回调 → 订单状态翻转 + 日志无「验签失败 / 解密失败」。
   - 出站签名验证：下单接口（统一下单）成功 + 商户平台可查到对应交易。
   - 分账回调同验（`profit-sharing` 端点）。
5. **回滚预案**：云托管回滚到含旧密钥的上一个版本（保留 ≥5 版本，见 §11.2）。
6. **变更登记**：在 `01-docs/21-安全审计报告.md` 追加记录（时间、原因、操作人、验证结果）。

**泄露应急**：立即按上述 1/3/4 步执行轮换（可跳过公告），并复查 audit 日志确认密钥被谁查看过。
