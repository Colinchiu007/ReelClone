### 2.2 代码重复问题

#### 2.2.1 JWT Strategy 重复（10 份）

10 个服务各有 `jwt.strategy.ts`，现状分 3 类：

| 类别                 | 服务                                                                        | 行数       | 问题                                                  |
| -------------------- | --------------------------------------------------------------------------- | ---------- | ----------------------------------------------------- |
| 薄封装 re-export     | admin/asset/benchmark/notification/order/template/workbench/billing（8 个） | 5 行       | 标记 `@deprecated`，应直接删除                        |
| 独立实现（死代码）   | auth-service                                                                | 94 行      | 实际使用 `AuthStrategyModule.forRoot()`，此文件未引用 |
| **独立实现（活跃）** | **user-service**                                                            | **112 行** | **与其他 9 服务完全不一致**                           |

**user-service 的安全语义不一致**:

| 安全校验项                     | 9 服务（共享策略） | user-service |
| ------------------------------ | ------------------ | ------------ |
| token type 校验                | ✅                 | ❌           |
| jti 黑名单                     | ✅                 | ✅           |
| 密码修改踢下线                 | ✅                 | ✅           |
| tokenVersion                   | ✅                 | ❌           |
| session family                 | ✅                 | ❌           |
| 用户状态校验（FROZEN/DELETED） | ❌                 | ✅           |

#### 2.2.2 billing.client.ts 重复（5+ 份近似拷贝）

## 5. 架构与依赖分析

### 5.1 依赖方向

- **libs 之间**: 无循环依赖，分层清晰（基础层 → 中间层 → 上层）

- **common lib**: 导出 30+ 模块，范围较大但属于基础设施聚合层，可接受

## 7. 重构方案

### 7.1 P0 — 安全/正确性修复

#### R-P0-1: 统一 user-service JWT 策略

**问题**: user-service 使用 112 行独立 JWT 策略，缺少 token type、tokenVersion、session family 校验。

**方案**:

1. 将 user-service 迁移到 `AuthStrategyModule.forRoot()`
2. 在 `AccessTokenStrategy` 中增加可选的 `userStatusCheck` 配置项
3. user-service 启用 `userStatusCheck: true`，保留用户状态校验（FROZEN/DELETED）

**涉及文件**:

## 附录: 架构亮点（保持不变）

以下架构设计质量优秀，重构时应保持不变：

1. **apps 之间无直接 import** — 微服务通过 HTTP 通信
2. **libs 依赖图无循环** — 分层清晰
3. **common → database 接口反转** — 通过 IConfigStore 解耦
4. **docker-compose.prod.yml 设计** — YAML anchors + 网络隔离 + 资源限制
5. **adapter 模式** — adapters-sms/adapters-wechat 实现 ADR-003
6. **workbench-service 薄 Facade** — generation.service.ts 委托给 Handler
7. **小程序 RequestManager** — 并发控制 + Token 刷新锁 + 统一错误处理
8. **小程序 useWebSocket** — 心跳 + 指数退避 + 防并发刷新锁
9. **billing-service ledger 测试** — 覆盖幂等性/异常/不变量
10. **E2E 测试设计** — 真实跨服务流程 + 幂等性 + JWT 互通验证

---

> **结论**: ReelClone 代码库整体质量中等偏上，架构设计合理。30 个重构项中 P0（4 项）应立即修复，P1（8 项）应规划在近期 sprint 中完成，P2/P3 可渐进改进。总工作量约 55.5 小时，建议分 4 个 Phase 在 1-2 个 sprint 内完成。
