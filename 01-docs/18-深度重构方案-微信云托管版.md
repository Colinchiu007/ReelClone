## 2. P0 安全/正确性修复

### R-P0-1: 统一 user-service JWT 策略

**问题**: user-service 使用 112 行独立 JWT 策略，缺少 token type、tokenVersion、session family 校验。

**方案**:

1. 将 user-service 迁移到 `AuthStrategyModule.forRoot()`
2. 在 `AccessTokenStrategy` 中增加可选的 `userStatusCheck` 配置项
3. user-service 启用 `userStatusCheck: true`，保留用户状态校验（FROZEN/DELETED）

**涉及文件**:

- [apps/user-service/src/auth/jwt.strategy.ts](file:///d:/Data/projects/ReelClone/apps/user-service/src/auth/jwt.strategy.ts)（删除）
- [apps/user-service/src/user/user.module.ts](file:///d:/Data/projects/ReelClone/apps/user-service/src/user/user.module.ts)（改用 AuthStrategyModule）
- [libs/common/src/auth/access-token.strategy.ts](file:///d:/Data/projects/ReelClone/libs/common/src/auth/access-token.strategy.ts)（增加 userStatusCheck）

**验证**: typecheck + unit test + E2E auth flow
**工作量**: 2h

### R-P0-2: 删除 auth-service 死代码

**方案**: 直接删除 [apps/auth-service/src/auth/jwt.strategy.ts](file:///d:/Data/projects/ReelClone/apps/auth-service/src/auth/jwt.strategy.ts)（94 行，未引用）。

**验证**: typecheck
**工作量**: 0.5h

### R-P0-3: 修复分层违规

**方案**:

- `profit-sharing-record.controller.ts`: 将 Repository 查询移到 `ProfitSharingService`
- `industry.controller.ts`: 创建 `IndustryService` 封装 User 表读写

**验证**: typecheck + unit test
**工作量**: 2h

### R-P0-Critical: 移除硬编码 localhost fallback

> ⚠️ **优先级从 P0 提升至 P0-Critical** — 云托管中服务间通过内网域名通信，localhost 绝对不工作。

**问题**: 以下文件有 localhost fallback，违反 ADR-003 fail-closed 原则：

| 文件                                                            | fallback 值               |
| --------------------------------------------------------------- | ------------------------- |
| `apps/workbench-service/src/workbench/billing.client.ts:48-51`  | `'http://localhost:3006'` |
| `apps/workbench-service/src/workbench/template.client.ts:49-52` | `'http://localhost:3004'` |
| `apps/workbench-service/src/app.module.ts:54`                   | `'localhost:7233'`        |
| `apps/benchmark-service/src/benchmark/billing-client.ts`        | localhost fallback        |
| `apps/template-service/src/template/billing.client.ts`          | localhost fallback        |
| `apps/order-service/src/order/billing.client.ts`                | localhost fallback        |

**方案**:

1. 移除所有 `|| 'http://localhost:XXXX'` fallback
2. 改为 `ConfigService.getOrThrow<string>('SERVICE_URL')`（缺失时启动即失败）
3. 云托管控制台配置内网域名作为环境变量

**涉及文件**: 5+ 个 billing.client.ts / template.client.ts / app.module.ts

**验证**: typecheck + unit test + 本地启动验证
**工作量**: 1h

## 3. P1 可维护性重构

### R-P1-1: 拆分 OrderService.handleCallback

**方案**: 将 270 行方法拆分为 5-6 个私有方法：

```
handleCallback()
  ├── verifyCallbackSignature()    — 验签
  ├── checkIdempotency()            — 幂等检查
  ├── verifyFieldBinding()          — 字段绑定校验
  ├── transactionalUpdate()         — 事务化状态更新
  └── postCommitCompensation()      — best-effort 调用
```

**验证**: typecheck + order.service.spec + E2E 004
**工作量**: 4h

### R-P1-2: 统一 billing.client.ts 到 InternalHttpClient

**方案**: 5+ 个 billing.client.ts 改为注入 `@reelclone/http-client` 的 `InternalHttpClient`（已有熔断器+重试）。统一命名为 `billing.client.ts`。

**云托管适配**: 服务间 URL 通过云托管控制台配置内网域名环境变量。

**验证**: typecheck + 各服务 spec
**工作量**: 4h

### R-P1-3: 抽取 bootstrapService() 工厂函数

**方案**: 在 `@reelclone/common` 中创建 `bootstrapService(options)` 工厂，统一 11 个 `main.ts` 为 3-5 行调用。

```typescript
bootstrapService({
  name: 'user-service',
  port: 3002,
  module: AppModule,
})
```

**验证**: typecheck + 11 服务启动验证
**工作量**: 3h

### R-P1-4: E2E 纳入 CI

**方案**:

1. CI 增加 `docker-compose up -d postgres redis temporal` 步骤
2. 运行 `npm run test:e2e`
3. 设置 E2E 作业依赖 Docker 构建（复用镜像）

> **注**: CI 中仍使用 docker-compose 启动依赖，与云托管部署无关。

**验证**: CI 绿
**工作量**: 4h

### R-P1-5: 补全 database 库测试

**方案**: 为 14 个 TypeORM 实体添加字段约束/关系测试，验证 snake-naming.strategy 转换逻辑。

**验证**: coverage 提升
**工作量**: 4h

### R-P1-6: 统一 Dockerfile 模板（云托管适配版）

> **简化**: 移除 HEALTHCHECK（云托管自动接管），但仍需统一模板。

**方案**: 创建 Dockerfile 模板：

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --legacy-peer-deps
COPY . .
RUN npx tsc -p apps/SERVICE/tsconfig.json

FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/apps/SERVICE/dist ./apps/SERVICE/dist
COPY --from=builder /app/package.json ./
# 云托管自动接管健康检查，无需 HEALTHCHECK
CMD ["node", "apps/SERVICE/dist/main.js"]
```

**验证**: Docker build 11/11
**工作量**: 3h

### R-P1-7: 统一 .env.example

> **简化**: 配置入口改为云托管控制台，但 .env.example 仍需作为开发文档。

**方案**:

1. 创建根 `.env.example` 作为权威配置模板
2. 各服务 `.env.example` 只包含该服务特有配置
3. 统一 DATABASE_PASSWORD、JWT_SECRET、微信支付变量名

**验证**: 人工验证
**工作量**: 2h

### R-P1-8: 修复 test:integration 脚本

**方案**: 修正 `package.json` 中 `test:integration` 脚本指向 `tests/integration/jest.config.js`，或删除此失效脚本。

**验证**: 脚本可执行
**工作量**: 0.5h

### R-NEW-1: Docker 镜像瘦身优化

> **新增项** — 云托管冷启动计费，镜像越小冷启动越快。

**方案**:

1. 多阶段构建，prod stage 仅包含 `node:20-alpine` + `node_modules` + `dist`
2. builder 阶段结束后 `npm prune --production --legacy-peer-deps` 移除 devDependencies
3. 完善 `.dockerignore` 排除 `test/`、`coverage/`、`.git/`、`node_modules/`、`01-docs/`
4. 考虑使用 multi-stage cache 优化构建速度

**预期效果**: 镜像体积从 ~800MB 降至 ~300MB，冷启动时间从 ~10s 降至 ~3s。

**验证**: `docker images` 查看大小
**工作量**: 3h

### R-NEW-2: Temporal 部署方案调研

> **新增项** — 云托管不适合运行 Temporal Server。

**方案**: 调研并选型 Temporal Server 的独立部署方案：

| 方案                            | 优点       | 缺点                 | 推荐度 |
| ------------------------------- | ---------- | -------------------- | ------ |
| A: Temporal Server 独立云服务器 | 无需改代码 | 增加服务器费用       | ⭐⭐⭐ |
| B: 改用消息队列（CMQ/Kafka）    | 云原生     | 需重写 workflow 逻辑 | ⭐⭐   |
| C: 异步任务表 + 轮询            | 最简单     | 延迟高               | ⭐⭐   |

**短期推荐**: 方案 A（Temporal Server 独立部署到云服务器）。

**输出**: Temporal 部署文档
**工作量**: 5h（调研 + 文档）

## 7. 风险评估

### 高风险

| 重构项                                | 风险                 | 缓解                                    |
| ------------------------------------- | -------------------- | --------------------------------------- |
| R-P0-1 user-service JWT 迁移          | 影响登录/鉴权        | E2E auth flow + 004 验证                |
| R-P0-Critical 移除 localhost fallback | 本地开发可能受影响   | 保留 .env 本地配置，仅移除代码 fallback |
| R-P1-1 拆分 handleCallback            | 微信支付回调逻辑复杂 | E2E 004 验证                            |
| R-NEW-2 Temporal 部署                 | 架构级风险           | 短期独立部署，不改代码                  |

### 中风险

| 重构项                        | 风险                 | 缓解         |
| ----------------------------- | -------------------- | ------------ |
| R-P1-2 统一 billing.client.ts | 跨 5+ 服务           | 逐个迁移     |
| R-P1-3 统一 main.ts           | 11 服务同时改        | 逐个迁移     |
| R-NEW-1 镜像瘦身              | npm prune 可能漏依赖 | 本地启动验证 |

### 低风险

| 重构项            | 风险 | 缓解             |
| ----------------- | ---- | ---------------- |
| R-P0-2 删除死代码 | 无   | typecheck        |
| R-P2 系列         | 低   | typecheck + lint |
| R-P3 系列         | 低   | typecheck + lint |

> **结论**: 微信云托管版重构方案共 32 项，比原方案多 2 项（+7h），主要新增镜像瘦身和 Temporal 调研。最大架构风险是 Temporal Server 的部署位置，建议短期独立部署。
