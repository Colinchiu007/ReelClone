# 微信云托管部署影响分析

> **生成时间**: 2026-08-07
> **背景**: ReelClone 目标部署平台为微信云托管（WeChat Cloud Run），而非传统 Kubernetes/Docker Compose 部署。本文档分析该决策对重构方案的影响。

---

## 1. 微信云托管 vs 传统部署

| 维度      | 传统 Docker/K8s                | 微信云托管                               |
| --------- | ------------------------------ | ---------------------------------------- |
| 容器编排  | docker-compose / K8s manifest  | 云托管控制台管理，无需 compose           |
| 服务发现  | Nginx 反向代理 / K8s Service   | 云托管内网域名自动分配                   |
| 健康检查  | Dockerfile HEALTHCHECK         | 云托管自动接管（仍需 HTTP /health 端点） |
| 镜像构建  | CI 构建推送 registry           | 云托管 CI 构建或上传镜像                 |
| 镜像 Tag  | digest / commit sha（ADR-004） | 云托管版本管理                           |
| 弹性伸缩  | K8s HPA                        | 云托管自动弹性                           |
| 请求路由  | Nginx / Ingress                | 云托管 API 网关                          |
| 环境变量  | .env / ConfigMap               | 云托管控制台环境变量配置                 |
| 日志/监控 | ELK / Prometheus               | 云托管日志 + 微信告警                    |

---

## 2. 对重构方案的影响

### 2.1 受影响的重构项

| 重构项                               | 传统部署                         | 微信云托管                                                        | 影响程度        |
| ------------------------------------ | -------------------------------- | ----------------------------------------------------------------- | --------------- |
| **R-P2-7 遵循 ADR-004**              | 需要修复 docker-compose.prod.yml | **不需要** — 云托管管理容器编排，无 docker-compose.prod           | 🔴 项可删除     |
| **R-P1-6 统一 Dockerfile**           | 需要 healthcheck                 | **仍需** — 但 healthcheck 机制由云托管接管                        | 🟡 简化         |
| **R-P0-4 硬编码 localhost fallback** | 有风险                           | **风险更大** — 云托管服务间通过内网域名通信，localhost 绝对不工作 | 🔴 优先级提升   |
| **R-P1-2 统一 billing.client.ts**    | 服务 URL 配置                    | **需适配** — 服务间调用用云托管内网域名                           | 🟡 配置方式不同 |
| **R-P1-7 统一 .env.example**         | 环境变量                         | **仍需** — 但配置入口是云托管控制台                               | 🟡 简化         |
| **Nginx 反向代理**                   | 需要                             | **不需要** — 云托管自带 API 网关                                  | 🔴 可删除       |
| **镜像大小优化**                     | 一般关注                         | **高度关注** — 云托管按实例+冷启动计费，镜像越小冷启动越快        | 🔴 新增项       |
| **admin-web 部署**                   | 独立部署                         | 可托管为静态资源                                                  | 🟢 简化         |
| **R-P1-4 E2E 纳入 CI**               | docker-compose 启动依赖          | **仍需** — CI 中仍用 docker-compose                               | 🟢 不变         |
| **Temporal 部署**                    | docker-compose                   | **需调整** — 云托管不支持 Temporal Server 长期运行                | 🔴 架构影响     |

### 2.2 调整汇总

| 调整类型   | 数量 | 说明                                                            |
| ---------- | ---- | --------------------------------------------------------------- |
| 可删除项   | 2    | R-P2-7（docker-compose.prod）、Nginx 反向代理                   |
| 优先级提升 | 1    | R-P0-4（localhost fallback → 致命风险）                         |
| 简化项     | 3    | R-P1-6（healthcheck 简化）、R-P1-7（.env 简化）、admin-web 部署 |
| 新增项     | 2    | 镜像瘦身优化、Temporal 替代方案调研                             |
| 不变项     | 1    | R-P1-4（E2E CI 仍需 docker-compose）                            |

## 3. 最关键的影响：Temporal

微信云托管是容器即服务（CaaS），**不适合运行 Temporal Server**（需要长期运行的 Worker + 可恢复的工作流引擎）。这会影响：

### 3.1 受影响的服务

| 服务                | 当前实现                      | 云托管影响                                        |
| ------------------- | ----------------------------- | ------------------------------------------------- |
| `media-worker`      | Temporal Worker（长驻进程）   | 云托管容器可运行，但 Temporal Server 需要外部部署 |
| `workbench-service` | Temporal Client 启动 workflow | 需改为其他异步机制                                |
| `benchmark-service` | Temporal Client 启动 workflow | 同上                                              |
| `template-service`  | Temporal Client 启动 workflow | 同上                                              |

### 3.2 可选替代方案

| 方案                             | 优点               | 缺点                                         | 推荐度 |
| -------------------------------- | ------------------ | -------------------------------------------- | ------ |
| **A: Temporal Server 独立部署**  | 无需改代码         | 需要一台云服务器运行 Temporal + 可见性数据库 | ⭐⭐⭐ |
| **B: 改用消息队列（CMQ/Kafka）** | 云原生，弹性好     | 需要重写 workflow 编排逻辑                   | ⭐⭐   |
| **C: 异步任务表 + 轮询**         | 最简单，无需中间件 | 延迟较高，无自动重试                         | ⭐⭐   |
| **D: 微信云托管定时触发器**      | 免费额度           | 仅适合定时任务，不适合用户触发型             | ⭐     |

**推荐**: 短期方案 A（Temporal Server 独立部署到云服务器），中期评估方案 B。

### 3.3 影响评估

- **代码改动**: 如果选方案 A，代码层面**无需改动**，仅需将 Temporal Server 部署到独立云服务器
- **配置改动**: `TEMPORAL_ADDRESS` 环境变量改为 Temporal Server 的公网/内网地址
- **成本**: 增加一台云服务器费用（约 ¥200-500/月，取决于 Temporal 负载）
- **运维**: Temporal Server 需要独立维护（升级、备份、监控）

## 4. 新增重构项

### R-NEW-1: Docker 镜像瘦身优化

**原因**: 云托管按实例+冷启动计费，镜像越小冷启动越快，费用越低。

**方案**:

1. 多阶段构建，prod stage 仅包含 `node:20-alpine` + `node_modules` + `dist`
2. `npm prune --production --legacy-peer-deps` 移除 devDependencies
3. 使用 `.dockerignore` 排除 `test/`、`coverage/`、`.git/`、`node_modules/`
4. 考虑使用 `node:20-alpine` 的 slim 变体

**预期效果**: 镜像体积从 ~800MB 降至 ~300MB，冷启动时间从 ~10s 降至 ~3s。

### R-NEW-2: Temporal 部署方案调研

**原因**: 微信云托管不适合运行 Temporal Server。

**方案**: 调研并选型 Temporal Server 的独立部署方案，输出部署文档。

### 5.1 删除的项

| 原编号 | 内容                                             | 原因                |
| ------ | ------------------------------------------------ | ------------------- |
| R-P2-7 | docker-compose.prod.yml 移除 build + 改用 digest | 云托管管理容器编排  |

### 5.2 提升优先级的项

| 原编号 | 原优先级 | 新优先级        | 原因                                    |
| ------ | -------- | --------------- | --------------------------------------- |

| 原编号    | 简化内容                                                      |

### 5.4 新增的项

| 新编号  | 内容                  | 优先级 |
| ------- | --------------------- | ------ |
| R-NEW-1 | Docker 镜像瘦身优化   | P1     |
| R-NEW-2 | Temporal 部署方案调研 | P1     |

---

## 6. 结论

微信云托管对重构方案的影响集中在 **部署/运维层面**，对 **业务代码层面影响较小**。主要变化：

1. **删除** 2 项（docker-compose.prod、Nginx）
2. **提升** 1 项优先级（localhost fallback）
3. **新增** 2 项（镜像瘦身、Temporal 调研）
4. **简化** 3 项（Dockerfile healthcheck、.env、admin-web 部署）

**最大架构风险**: Temporal Server 的部署位置。建议短期独立部署，中期评估消息队列替代方案。
